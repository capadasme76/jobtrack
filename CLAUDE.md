# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this repo is

**JobTrack** is a live, deployed job-search dashboard for executive job seekers (pipeline de postulaciones, red de contactos, match de CV, reuniones, métricas, portales), running at **[jobtrack.cl](https://jobtrack.cl)**. It started as a static-HTML prototype and is now a real multi-user product: Supabase for auth/database, Vercel for hosting (auto-deploys on push to `main`), Cloudflare for DNS, and a Vercel serverless function for AI-assisted CV parsing. There is still no build system or bundler — every page is a self-contained HTML file, edited directly.

Everything else (`Avance 1/`, `Tester 5/`, `Tester 6/`, `Tester 7/`, `tester 2/`, `tester 3/`, `tester 4/`, `diseño/`) holds earlier iterations, exported snapshots, and zip archives from previous design passes — treat these as historical/reference material, not code to maintain. Don't edit files inside those folders unless the user explicitly asks you to work on a specific snapshot.

[JobTrack_Prompt_Claude_Design.md](JobTrack_Prompt_Claude_Design.md) is the original design brief (in Spanish) that specifies the pages, layout, color palette, and typography — consult it when making visual/design decisions. `diseño/design_handoff_jobtrack/` has the fuller original Home page design that `index.html` was rebuilt from.

## Site map

| File | Purpose |
|---|---|
| `index.html` | Public marketing Home — hero, feature grid, "Quiénes somos", FAQ + keyword-matching contact bot, Contáctanos. SEO metadata (OG/Twitter/JSON-LD) lives here. |
| `login.html` | Login/signup (Supabase Auth). Signup mode never auto-redirects on an existing session — see "Known-tricky areas" below. |

| `terminos.html`, `privacidad.html` | Términos y Condiciones / Política de Privacidad. Drafts referencing Ley N° 21.719 (Chile's data protection law, in force Dec 2026) — explicitly marked as needing real legal review, not a substitute for one. |
| `supabase-config.js` | Exports `SUPABASE_URL` / `SUPABASE_ANON_KEY` (anon key is public by design — RLS does the real access control). Imported by `login.html`, the dashboard, and `api/extract-cv.js`. |
| `supabase-schema.sql` | The `jobtrack_state` table + RLS policy. Run manually in the Supabase SQL editor — there's no migration tooling. |
| `api/extract-cv.js` | Vercel serverless function (Node, ESM). See "AI CV extraction" below. |
| `api/check-watched-search.js` | Vercel serverless function — manual "Comprobar ahora" trigger for a watched search, using the caller's own access token (not service_role). See "Watched searches" below. |
| `api/suggest-search-terms.js` | Vercel serverless function — proposes cargo/keyword variants from the user's profile (same auth + Claude Haiku forced-tool-call pattern as `extract-cv.js`). See "Watched searches" below. |
| `scripts/check-watched-pages.mjs` | Node script run by `.github/workflows/check-watched-pages.yml` on a daily cron. See "Watched-page checker" below. |
| `robots.txt`, `sitemap.xml` | Only `index.html` (and the legal pages) are indexable; `login.html` and the dashboard are `noindex`. |
| `package.json` | Exists only so Vercel treats `api/*.js` as ES modules (`"type": "module"`) — no dependencies, no build script. Doesn't affect the static HTML files at all. |

## Working locally

No build/lint/test command for the static pages:

```bash
python3 -m http.server 8000
```
then visit `http://localhost:8000/jobtrack-dashboard-cristian.html`. This serves the static files fine, but **cannot run `api/extract-cv.js`** (that's a real serverless function) — test that endpoint against a production/preview deploy instead, or use `vercel dev` if you need it locally.

**Validate changes**: no automated tests. Check the browser console for JS errors (everything runs inline, no framework/TypeScript to catch mistakes at write-time), and exercise the relevant section end-to-end.

## Architecture (jobtrack-dashboard-cristian.html)

Single file: inline `<style>`, then HTML markup for all sections, then `<script type="module">` (an IIFE, with `supabase`/`currentUserId` declared at module top level outside it so the whole file can import ES modules). No frameworks — vanilla JS, direct DOM manipulation (`document.getElementById`, manual `innerHTML` rendering).

**Navigation is a tile home screen + full-screen sections, not a scrolling page (changed 2026-08 — see "Known-tricky areas").** A tester found the old single continuously-scrolling page (all 10 sections stacked, sidebar just `scrollIntoView`-ing to an anchor) overwhelming. Now: `#jt-home` shows a grid of clickable `.jt-tile` cards (one per `SECTIONS` entry, `initSectionViews()`/`showSection()`/`showHome()`/`goToSection()`), and clicking one hides `#jt-home` + hides every other `.jt-module` and shows only that one, full-screen, with a "← Volver" button (`#jt-back-btn`) back to the grid. **DOM order of the `.jt-module` blocks no longer determines what the user sees first** — `SECTIONS` (a JS array) is now the single source of truth for section order/icons/labels, and it must be kept in sync by hand with the sidebar's static `<a href="#sec-*">` list (`.jt-nav`, `:368-377` roughly) — a duplication accepted deliberately to keep the tile-nav diff small; a future cleanup could generate the sidebar from `SECTIONS` too. Current order (both places): Hoy → Búsquedas de empleo → Mi perfil → Pipeline (agenda) → Match CV → Reuniones → Mis contactos → Métricas → Portales → Guía. "Current view" = `location.hash` (no separate JS state variable, no router lib) — `syncViewFromHash()` runs on load and on `hashchange`, so reloading or sharing a link with `#sec-pipeline` in it lands directly in that section. Every place that used to `scrollIntoView` a section (sidebar links, `.jt-guide-link`s, "Primeros pasos" items) now calls `goToSection(id, anchorId?)` instead — the optional second arg still does an in-section `scrollIntoView` to a specific card/row (e.g. a Hoy task jumping to `#opp-{id}`). Mi perfil's collapsible body still auto-expands when you navigate into it (`setProfileSectionExpanded(true)`, now centralized inside `showSection()` instead of repeated at every call site). `#jt-onboarding-card` and `.jt-mast` are hidden whenever a section is open (they belong to the home view) — `renderOnboarding()` itself also checks `#jt-back-btn`'s visibility before deciding to show the card, so a mutation-triggered re-render while browsing a section can't pop it back open behind the section content.

**Auth & persistence**: `supabase.auth.getSession()` gates everything — `loadState()` redirects to `login.html` if there's no session. `persist()` upserts the entire `state` object as one JSONB blob per `user_id` into the `jobtrack_state` table (RLS: `auth.uid() = user_id`). No partial updates — every mutation re-saves the whole state.

**State**: a single global `state` object (`opportunities`, `networking`, `meetings`, `profile`, `profileCvVersion`, `onboarding`, `onboardingDismissed`, `watchedPages`, `watchedSearches`). There is no stored `dispatches`/`dismissedDispatchIds` anymore (removed 2026-08 — see "Hoy is computed, not stored" below); `seedOpportunities`/`seedNetworking`/`seedMeetings` are deliberately empty arrays — every new account starts with a fully empty dashboard, no example records. There was a real incident where these seeds held actual personal data (real LinkedIn application URLs, a real target-company/contact list) hardcoded into this public static file and shown to every new signup as if it were placeholder content; `loadState()` also carries a one-time cleanup that strips those specific known-leaked entries from any account that was seeded before the fix (matched by exact link/name+empresa signatures, never touching a real user's own data). Only `seedProfile` still ships instructional placeholder *text* (e.g. "Tu cargo o especialidad (ej. Gerente de Marketing)") since that's form guidance, not a fake data record. `profileCvVersion` gates one-time forced profile re-seeds — bump that string when the seed profile shape changes and needs to override previously saved state. `onboarding` is a set of boolean flags (profile/opportunity/contact/match/meeting) driving the "Primeros pasos" checklist shown above Hoy for new users — existing accounts predating this field get `onboardingDismissed = true` on load instead of seeing it retroactively.

**Render pipeline**: each data section has its own `render*()` function (`renderProfile`, `renderStats`, `renderHoy`, `renderBoard`, `renderNetworking`, `renderMeetings`, `renderMetrics`, `renderTicker`, `renderMasthead`, `renderEdition`, `renderHome`). `renderAll()` calls all of them (order-independent except `renderHoy()` must run before `renderHome()`, since it sets `lastHoyTaskCount` for the Hoy tile's badge — each otherwise writes only to its own DOM ids) and runs after `loadState()` resolves, then again after each mutation followed by `persist()`. No diffing — each render fully rebuilds its section's `innerHTML`. Every `render*()` is safe to call while its section is `display:none` (hidden by the tile navigation) — none of them measure layout or depend on visibility, they just set `innerHTML`/`textContent` on ids that still exist in the DOM.

**Event wiring**: `wireForms()`, `wireIO()`, `wireNav()` attach all listeners once at startup. New interactive elements need listeners added in the relevant `wire*()` function, not inline `onclick`.

**Hoy is computed, not stored**: there is no `state.dispatches` array anymore. `computeHoyTasks()` builds the list fresh on every render by scanning `state.opportunities` (incompletas via `isIncomplete()`, vencidas/por vencer via `daysUntil(o.fechaLimite)`, seguimientos atrasados ≥7 días via `daysSince(o.fechaContacto)` — all three reuse the same helpers `renderBoard()` already used for its own badges), `state.watchedSearches`/`state.watchedPages` (a `lastChangedAt` newer than `lastReviewedAt`, a new per-entry field defaulting `null`, counts as an unreviewed task), and a simple "0 reuniones este mes" networking nudge. `renderHoy()` renders the list and wires `data-hoy-goto` (calls `goToSection()` + marks the underlying watch `lastReviewedAt` if it's watch-based) and `data-hoy-dismiss` (watch-based tasks only — agenda-based tasks like "incompleta"/"vencida" have no dismiss, they stay true until the underlying fact changes, same as before). This means the two backend checkers (`scripts/check-watched-pages.mjs`, `api/check-watched-search.js`) only ever write `hash`/`lastCheckedAt`/`lastChangedAt` on a watch entry now — neither pushes a dispatch record; the dashboard is what turns those fields into a task list.

**Sections**: Hoy (stats + computed task list, see above), Mi perfil (collapsed by default, `jt-collapsible-title` pattern; sub-sections Experiencia/Formación/Carta also collapse individually via `profileExpanded`), Búsquedas de empleo (always-visible, see "Watched searches" below), Pipeline (user-facing label is "Agenda de postulaciones" — a tester found "Pipeline" confusing English jargon, renamed 2026-08 across the dashboard, Home, and legal pages; internal id/class/variable names (`sec-pipeline`, `.jt-board`, `renderBoard()`) intentionally kept as-is, don't rename those too) (kanban board, stage change is a per-card `<select class="jt-status-select">`, not native HTML5 drag/drop — deliberately, since drag/drop doesn't work on touch; columns cap at `max-height:600px` with their own scroll on desktop only — see "Known-tricky areas", Excel import/export via SheetJS CDN, moved below the board as a secondary action), Match CV (`runMatchAnalysis` — client-side text/keyword matching, no external API — the result includes an explicit disclaimer that it's not a real fit evaluation), Reuniones, Mis contactos (own Excel template/import, plus a name/company search box), Métricas (didactic: % of total per stage, color-coded, tooltips), Portales (static external job-board links), Guía (static how-to reference, 9 numbered steps matching the section order above, each linking to its section).

**Georeferenciación**: `region` field (16 Chilean regions, `CHILE_REGIONS`/`regionOptionsHtml()`) on opportunities and contacts, with a Pipeline filter and Excel column.

**AI CV extraction**: "Mi perfil → Editar" has a CV upload (PDF/`.docx` only, not legacy `.doc`). Text extraction happens **client-side** (pdf.js / mammoth.js, CDN-loaded) — the file itself is never uploaded anywhere. The extracted text is POSTed to `/api/extract-cv` with the user's Supabase access token; that function verifies the token against Supabase before calling Claude (`claude-haiku-4-5-20251001`, forced tool-calling for structured JSON) and returns fields matching `state.profile`'s shape. The response only pre-fills the edit-form fields — nothing is saved until the user reviews and clicks "Guardar perfil".

**Watched-page checker (Fase 2)**: opportunities can optionally have a `careerUrl` (the company's general jobs page, distinct from `link` which is the specific posting) — kept in sync via `syncWatchedPage()`/`removeWatchedPage()` into `state.watchedPages`. `scripts/check-watched-pages.mjs` runs daily via GitHub Actions, hashes each watched page's normalized text, and — only on a detected change — updates `hash`/`lastCheckedAt`/`lastChangedAt` on that watch entry via Supabase's REST API (service_role key, bypasses RLS by design); it no longer pushes a dispatch record (see "Hoy is computed, not stored" above) — the dashboard's `computeHoyTasks()` picks up the change from those fields on its own. Explicitly skips any `linkedin.com` URL (scraping LinkedIn violates their ToS). This replaced an earlier plan to aggregate real job postings — validated that Greenhouse/Lever/Ashby/datos.gob.cl have zero API coverage for this product's target companies (large traditional Chilean employers), so full aggregation isn't viable without a paid API, which was explicitly ruled out.

**Watched searches**: "Búsquedas de empleo" (its own top-level section, not nested in Mi perfil) generates a ready search-results link **per cargo, in every portal in `SEARCH_PORTALS`** (ChileTrabajos, LinkedIn, Indeed, Laborum, Trabajando.cl) — the user clicks through and filters/builds their own pipeline manually, the same self-service pattern already used for LinkedIn. Real backend monitoring (daily hash-diff + manual "Comprobar ahora") only exists for the one portal in that list flagged `monitored:true` — **ChileTrabajos**, the only one a server-side fetch can actually read: Indeed 403s automated requests, Laborum/Trabajando.cl are client-rendered SPAs that return an empty shell to a plain fetch (their `buildUrl` formats were confirmed instead by driving a real browser — GET-based, no server round-trip needed since a human's browser renders them fine), LinkedIn is ToS-prohibited, and **Computrabajo returns real content to a request from a local machine but 403s the same request from Vercel's or GitHub Actions' IP ranges** — confirmed live in production, not just guessed — so it's excluded from `SEARCH_PORTALS` entirely (not even as a link) since it can't reliably serve results to a general audience either. Each `state.watchedSearches` entry carries `monitored`, `cargo`, and `portalLabel` (kept explicit rather than parsed back out of the display `label` string) — `scripts/check-watched-pages.mjs` and `api/check-watched-search.js` both skip any entry with `monitored:false` before ever attempting a fetch. `api/suggest-search-terms.js` proposes 5-8 cargo variants (synonyms, seniority, adjacent roles) from the user's `tituloProfesional`/`resumen`/`habilidades` via Claude — the "Sugerir términos según mi perfil" button renders them as a checklist so search terms don't rely on the user thinking of every synonym themselves; picking terms (suggested or typed, comma-separated for several at once) calls the shared `generateSearchesForCargos()` helper, which skips cargo+portal combos that already exist so re-generating never creates duplicate rows. `check-watched-pages.mjs` hashes ChileTrabajos results the same way as `watchedPages`, stripping dates/times/weekday names from the normalized text first (`DATE_NOISE_RE` — a page's own "hoy es viernes 21..." banner otherwise looks like a change every single day) before comparing hashes, so a genuinely-repeating-but-cosmetic change doesn't false-positive as new content every day. There's also a manual per-search trigger — `api/check-watched-search.js`, called from a "Comprobar ahora" button next to each watched search — so users aren't stuck waiting for the once-a-day cron; it authenticates with the user's own access token (not service_role) and reads/writes only their own `jobtrack_state` row under RLS, applying the same date-noise stripping. An email alert on top of the in-app Hoy task (via Resend) is planned but not built — would need a `RESEND_API_KEY` GitHub Actions secret and a Supabase auth-admin lookup to resolve each user's email from their `user_id`.

**Word export**: `downloadWordDoc()` builds a minimal HTML-as-.doc file (MIME trick, not a real docx) — used by `exportProfileToWord()`/`exportCartaToWord()`.

## Known-tricky areas (read before touching)

- **Signup session hijack**: `login.html` used to auto-redirect to the dashboard on *any* existing Supabase session, even mid-signup — meaning a tester on a browser with a leftover session got dropped into someone else's account before they could submit the signup form. Fixed: signup mode now shows a "close this session first" notice instead of redirecting silently. Don't reintroduce a blind `getSession() → redirect` on the signup path.
- **Pipeline scroll**: `.jt-col` has `max-height:600px; overflow-y:auto`, and `.jt-board` uses `align-items:start` (CSS Grid defaults to `stretch`, which used to force every column to match the tallest one's height). If Pipeline columns start looking wrong again, check these two rules first.
- **Two different "link" fields on an opportunity**: `link` is the specific job posting (for "Postular"), `careerUrl` is the company's general jobs page (for the watched-page checker). Users found these confusing before the fields were relabeled — keep the labels explicit if touched again.
- **Only `link` is required** when adding an opportunity — `empresa`/`cargo`/`sector` default to placeholder text ("Empresa por confirmar", etc.) and the opportunity gets auto-flagged `incompleta: true` if left blank. Don't reintroduce a hard requirement on those fields.
- **Every Hoy task needs a way out, or a reason it can't have one**: `renderHoy()`'s tasks split into two kinds — watch-based (`watchedSearch`/`watchedPage`) get a "Descartar" button that sets `lastReviewedAt` on the underlying watch entry, since a false-positive change the user doesn't care about would otherwise nag forever; agenda-based (`incompleta`/`vencida`/`porvencer`/`seguimiento`) deliberately have **no** dismiss — they represent a fact that's still true (a field really is empty, a deadline really did pass) and should stay visible until the user actually fixes the underlying opportunity, not be swept aside. Don't add a blanket "dismiss all" without preserving this distinction.
- **Never hardcode real personal data as "example" seed content**: this HTML file is static and publicly fetchable without a session (`curl`/"view source" works on anyone, logged in or not) — `robots.txt`'s `noindex` only tells crawlers not to index it, it doesn't block direct fetches. `seedOpportunities`/`seedNetworking`/`seedDispatches` once held Cristian's real LinkedIn application URLs and real target-company/contact list as if they were placeholder demo data; they're now deliberately empty (see "State" above). Any future "example" content in this file must be obviously fictional (`"[Ejemplo] Empresa A"`, generic titles) — never a real company name tied to a real strategy, a real URL, or anything that identifies a real person.
- **Secrets**: Supabase `service_role` key lives only as a GitHub Actions secret (`SUPABASE_SERVICE_ROLE_KEY`) and is easy to confuse with the `anon` key or Supabase's newer `sb_secret_...` format (same project, different key system — the classic JWT-based anon/service_role pair is under Supabase's "Legacy API keys" tab now). `ANTHROPIC_API_KEY` lives only as a Vercel environment variable. Neither should ever be hardcoded or imported into client-facing code — `supabase-config.js` intentionally only exports the public anon key.
